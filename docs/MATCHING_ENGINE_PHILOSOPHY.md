# VoxBridge Matching Engine — Philosophy

> Зафиксировано 25.07.2026 из research-размышлений.  
> **Не ломает текущий код.** Описывает, *как мы думаем*, и куда двигаемся маленькими шагами.

---

## Главная идея

VoxBridge **не** создаёт собственную модель распознавания голоса с нуля.

Задача — **объединить** лучшие доступные (open-source / позже коммерческие) инструменты анализа голоса в систему **музыкального мэтчинга**.

| Мы не отвечаем | Мы отвечаем |
|----------------|-------------|
| «Это один и тот же человек?» | «Насколько этот вокалист подходит для исполнения конкретной AI-вокальной партии?» |

**IP проекта** — не нейросеть, а **система принятия решений**: какие модули, какие веса, как собрать Match Score и объяснить его.

---

## Философия «больница, не один врач»

Не «100 агентов-чатботов».  
А **независимые специалисты** — каждый отвечает только за свою область:

| Специалист | Отвечает за | Сегодня в коде (v0) |
|------------|-------------|---------------------|
| Embedding | Цифровой отпечаток голоса | ECAPA / SpeechBrain |
| Pitch | Диапазон, тесситура | librosa pitch features |
| Timbre | Окраска | MFCC + spectral shape |
| Recording Quality | Шум, клип, SNR — **не** «плохой голос» | `quality_score` |
| Vocal Style | Подача (мягкая / агрессивная…) | vocal character (частично) |
| Language | Язык / акцент | анкета / имя файла; auto lang-id на пении слабо |
| **Scoring (VoxBridge)** | Как сложить ответы в Match | `combine_scores` + веса + feedback |

Каждый специалист **не знает** о других.  
Только **Scoring Engine** собирает ответы → Match Score + объяснение.

Сходство голоса **≠** пригодность для проекта.  
Даже при сильном тембре могут не подойти диапазон, стиль, язык, манера.

---

## Три фильтра на любую новую идею

1. **Уже существует?** → используем (лицензия + качество ок).  
2. **Увеличит качество мэтчинга?** → иначе откладываем.  
3. **Проверяется экспериментом?** → иначе не в план.

Не плодим бесконечный wishlist. Развиваемся как инженерная система.

---

## Пол человека ≠ тембр записи

- **Пол** — характеристика человека (анкета вокалиста), не вывод модели по файлу.  
- **Воспринимаемый тембр / тип подачи** — про запись.  
Женщина может звучать «ниже/плотнее»; мужчина — «выше/ярче».  
Алгоритм не должен «назначать пол человека» только по аудио.

*(Сейчас в lab ещё есть эвристики/фильтры по полу для демо — это переходный слой; цель — анкета + отдельный timbre type.)*

---

## Recording quality отдельно

Плохая запись ≠ плохой голос.  
Quality-модуль не должен автоматически убивать Match так же, как промах по тембру.

---

## Объяснимый Match

Мало показать `91%`. Нужны отдельные показатели: тембр, диапазон, стиль, качество записи, embedding…  
Пользователь понимает *почему*.

---

## MVP и исследования

1. Готовые модели + свой датасет (AI-вокалы, легальные акапеллы, **оценки ухом**).  
2. Понять, что работает.  
3. Только потом — свои компоненты там, где gap доказан.  
4. Эксперты (педагоги, звукорежиссёры) — **после** появления узких вопросов, не вместо тестов.

Калибровка Да/Нет и дуэли на `/results` — часть Scoring Engine (human-in-the-loop), не побочный UI.

---

## Как менять модуль позже

См. пакет `voice-matching-service/matching_modules/`.

Сегодня внутри специалиста — одна реализация.  
Через полгода вышла лучше → меняем **один** модуль, scoring и остальное продолжают работать.

---

## Что это значит для ежедневной работы

- Не сносить текущий `main.py` ради «идеальной архитектуры».  
- Резать границы тонко: контракты → потом замена реализаций.  
- Ухо продюсера / основателя — главный эксперимент для весов.  
- Cursor внедряет модули; человек решает «ок / не ок» и слушает.
