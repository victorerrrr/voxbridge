## Часть 1. Что такое VoxBridge (для всех)

### Идея одной фразой

VoxBridge — это маркетплейс, который соединяет музыкальных продюсеров с реальными вокалистами, используя ИИ для подбора голоса по звучанию, а не по тегам и описаниям.

### Проблема, которую решает платформа

Продюсер пишет трек, у него есть референс — голос ИИ-генерации (например, из Suno) или просто пример звучания, которое он хочет. Дальше ему нужен **настоящий человек**, который может исполнить вокал похожим тембром, диапазоном, манерой.

Сегодня это решается вручную: продюсер listens к десяткам портфолио на сайтах вроде SoundBetter, читает описания "тёплый альт, R&B, мягкая подача" — и угадывает. Это медленно и субъективно.

### Что делает VoxBridge иначе

Продюсер загружает аудио-референс (голос, который он хочет услышать). Платформа **слушает** этот референс и сравнивает его акустически — высоту голоса, тембр, манеру — с записями реальных вокалистов в базе. Результат — ранжированный список: кто звучит ближе всего, и почему именно (не "у нас совпадают теги", а "по тембру совпадение 92%, по высоте голоса — 85%").

Это и есть главное технологическое отличие платформы от конкурентов — **настоящий звуковой анализ**, не текстовый поиск.

### Кто использует платформу

- **Продюсер** — загружает референс, получает список подходящих голосов, выбирает вокалиста, оформляет заказ, получает готовую запись.
- **Вокалист** — заполняет профиль (жанры, диапазон, примеры голоса), получает запросы от продюсеров, которым подходит его голос, договаривается, выполняет заказ.
- **Администратор** — модерирует платформу, разбирает жалобы, управляет пользователями.

## Часть 2. Как это устроено изнутри (для всех, без жаргона)

Представь платформу как дом с тремя основными комнатами.

### Комната 1 — "Слушающая машина" (мозг подбора голосов)

Это отдельная программа, которая занимается только одним — слушает два аудиофайла и говорит, насколько они похожи. Она использует готовые, проверенные технологии распознавания голоса (используемые, например, в системах безопасности по голосу), а не что-то придуманное с нуля.

Она смотрит на несколько характеристик одновременно:
- **Тембр** — "текстура" голоса (самый важный фактор)
- **Высота голоса** — диапазон, в котором поёт человек
- **Характер исполнения** — манера, окраска голоса
- **Качество записи** — насколько чистый звук

Эта часть платформы **уже полностью готова и работает** — это самая сложная техническая часть, и она была сделана первой, потому что без неё вся идея платформы не имеет смысла.

### Комната 2 — Витрина и личные кабинеты

Это то, что видит пользователь — сайт, формы, кнопки, страница поиска вокалиста, личный кабинет, переписка с заказчиком. Это сделано и работает визуально полностью.

### Комната 3 — Хранилище данных (где живёт вся информация)

Вот здесь — главная новость этого этапа работы. **До сих пор все данные (профили пользователей, заказы, переписка) хранились не в общей базе, а прямо в браузере конкретного человека** — как если бы каждый посетитель магазина писал список покупок в своём личном блокноте, который никто другой не видит.

Это означало: если ты регистрировалась на одном компьютере, зайти со второго и увидеть тот же профиль было невозможно. Два разных человека физически не могли увидеть данные друг друга через платформу — каждый видел только свою изолированную копию.

**Это и есть тот этап, который мы закрываем прямо сейчас (конец июня 2026)** — переносим все данные в настоящую, общую базу данных (Supabase), чтобы платформа стала действительно многопользовательской, как любой нормальный сайт.

## Часть 4. Что происходит прямо сейчас (июнь 2026)

Мы переводим платформу с "блокнота в браузере" на настоящую общую базу данных — сервис называется **Supabase** (это готовая, надёжная инфраструктура, используемая тысячами проектов, не самописное решение).

### Что уже сделано на этом этапе:

1. **Создана настоящая база данных** — 10 таблиц, которые соответствуют всем сущностям платформы: пользователи, профили вокалистов, заказы, запросы, отзывы, переписка, жалобы.
2. **Включена защита данных** — каждая таблица защищена правилами доступа (кто что может видеть и менять). Например: продюсер видит только свои заказы, вокалист — только свои, админ — видит всё для модерации. Это сделано построчно для каждой таблицы — итого 39 правил безопасности.
3. **Система входа переведена на настоящую авторизацию** — больше не "псевдо-логин" с паролем, видимым в коде, а настоящая, безопасная система входа (через email), та же технология, что использует большинство современных сервисов.

### Что осталось на этом этапе:

1. Проверить вживую в браузере, что регистрация и вход реально работают через новую систему.
2. Создать первую административную учётную запись (вручную, через панель Supabase).
3. Перевести оставшиеся данные (профили вокалистов, заказы, отзывы) с "блокнота в браузере" на настоящую базу — сегодня переехала только система входа, остальное ещё предстоит.

## Часть 6. Технический раздел (для специалистов)

### Стек технологий

| Слой | Технология |
|---|---|
| Frontend | Next.js 16 (React 19, TypeScript, Tailwind CSS 4) |
| ИИ-анализ голоса | Отдельный Python-сервис (FastAPI) — SpeechBrain ECAPA-TDNN (распознавание голоса), Demucs (разделение вокала от музыки), librosa (анализ высоты/тембра) |
| База данных и авторизация | Supabase (Postgres + Auth), free tier, регион eu-west-2 (Лондон) |
| Репозиторий | github.com/victorerrrr/voxbridge.git, рабочая ветка `home-rebuild-v2` |

### Архитектура матчинга (как именно сравниваются голоса)

Каждый голос разбивается на несколько акустических признаков, которые сравниваются отдельно и затем складываются с разными весами:

| Признак | Вес (стандартный режим) | Что измеряет |
|---|---|---|
| Тембр | 42% | "Текстура" голоса — самый весомый фактор |
| Высота голоса (pitch) | 30% | Диапазон и характерная высота |
| Идентичность голоса (speaker) | 15% | Узнаваемость голоса как такового |
| Характер вокала | 8% | Дополнительные стилистические черты |
| Качество записи | 5% | Чистота звука |

Веса автоматически меняются в зависимости от выбранного стиля (например, для рэпа важнее идентичность голоса, для оперы — высота и диапазон) — это управляется фильтром "Voice Style" на странице поиска.

### Структура базы данных (10 таблиц)

| Таблица | Назначение |
|---|---|
| `users` | Базовая информация о пользователе (email, имя, роль: продюсер/вокалист/админ) |
| `vocalist_profiles` | Профиль вокалиста — теги, диапазон, оборудование, биография |
| `vocalist_demos` | Демо-записи, привязанные к профилю |
| `orders` | Заказы — статус, бюджет, привязка продюсер↔вокалист |
| `vocalist_requests` | Запросы от продюсера к вокалисту до превращения в заказ |
| `reviews` | Отзывы продюсеров о вокалистах |
| `admin_reports` | Жалобы для модерации |
| `moderation_items` | Очередь модерации (демо, профили, ссылки) |
| `conversations` / `messages` | Переписка внутри рабочего пространства |

### Безопасность данных (RLS — Row Level Security)

Каждая таблица защищена правилами на уровне базы данных (не просто на уровне кода сайта — это защита, которую невозможно обойти даже при ошибке в коде фронтенда). Общий принцип:
- Публичные данные (профили вокалистов, демо, отзывы) — видны всем.
- Личные данные (заказы, переписка, запросы) — видны только участникам конкретной сделки.
- Администраторы (роль `admin` в таблице `users`) — видят и могут модерировать всё, независимо от других правил.

Любое количество людей может иметь роль администратора одновременно, каждый под своей учётной записью, с любого устройства — это не привязано к конкретному компьютеру или браузеру.

### Принятые архитектурные решения и почему

- **Вход только по email**, без логина по username — стандарт для современных платформ (изучен подход конкурентов вроде Suno), упрощает систему безопасности.
- **Гибридная схема хранения тегов** — массивы строк (а не отдельные таблицы) для гибких списков типа жанров, что даёт быстрый поиск без избыточной сложности.
- **Матчинг-движок не переписывался** при переходе на новую базу — он уже был сделан правильно и работает отдельно от остальной системы; переезжает только то, что хранит профили/заказы/переписку.
